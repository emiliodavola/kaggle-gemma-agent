# LoRA SFT on a 3090: plan

## Why this, and not more prompt work

Two runs of the same agent on the same 129 tasks bracket the prompt's ceiling.
`runs/20261101T021024Z` resolved 13 and `runs/20261101T192008Z` resolved 10, after
a change that made the pre-submit checks mechanical. The change did what it was
asked to do — `scratch` fell from 18 to 9 patches — and the score did not move.

The trace analysis says why. The compile gate ran in **113 of 129** tasks and in
**110** of them it ran after the last edit, returning `COMPILE_OK`:

```json
{"status": "ok", "stdout": "COMPILE_OK\n", "stderr": "", "exit_code": 0}
```

Thirteen of the eighteen tasks that still shipped unparseable Python had run that
gate last. The model obeys the command and ignores what it means. The remaining
failure mass is `AssertionError` (48 of 119): the patch parses, applies, and does
the wrong thing. That is capability, and no wording fixes capability.

## Why not go back to the 31B

Same submission tree, different base model:

| Run | Model | Tasks | Resolved | Mean min/task | Sum |
|-----|-------|------:|---------:|--------------:|----:|
| `20261030T111732Z` | 31B | 122 | 30 | 22.8 | 46.4 h |
| `20261101T021024Z` | E4B | 129 | 13 | 5.0 | 10.7 h |
| `20261101T192008Z` | E4B | 129 | 10 | 4.6 | 10.0 h |

The 31B resolves twice as often per task and takes 4.6 times longer. The scored
run has **12 hours for the whole hidden set** and behaves sequentially — our only
submission died with *"exceeded the allowed runtime"* under a 60-minute per-task
cap. At 22.8 min/task the 31B finishes about 31 of ~116 tasks; even at a 0.246
per-task rate that is `31 x 0.246 / 116 = 0.066`, below the E4B's 0.101 with every
task completed. Throughput, not quality, is what binds.

## Target

Beat the E4B baseline on the same corpus, same budgets, same harness. A useful
bar is **0.15 on the 129 public tasks** (19-20 resolved, against 10 today), with
the adapter staying under the contract (one base model, rank <= 128, < 3 GiB).

## Hardware envelope: one RTX 3090, 24 GB

Measured, not assumed: the unquantized
`google/gemma-4/transformers/gemma-4-e4b-it` checkpoint is **16,024,808,340 bytes
(~16 GB)** on the Kaggle model page. That is the bf16 weight budget, which puts
the model at roughly 8B stored parameters; the "4E" describes the effective size
of the architecture, not the number of weights on disk. The quantized competition
checkpoint the scorer serves is documented at ~3-4 GB in the harness README.

| Configuration | Weights in VRAM | Verdict on 24 GB |
|---------------|----------------:|------------------|
| Inference, quantized w4a16 | ~3-4 GB | comfortable |
| Inference, bf16 | ~16 GB | fits, but leaves no room for a 32k cache |
| LoRA in bf16 over the unquantized checkpoint | ~16 GB + activations | **borderline: measure in S4** |
| QLoRA, 4-bit NF4 base + bf16 adapters | ~4-5 GB | comfortable at 8k context |
| Full fine-tune | 16 GB + gradients + optimizer state | no |

The bf16 route leaves about 8 GB for activations, so it is a question of sequence
length and gradient checkpointing, not of principle: at 4k it most likely fits, at
8k it is doubtful. S4 measures it before the plan commits either way. QLoRA is the
default because it removes that risk at the cost of one approximation, described
next.

### Two quantizations, and they are not the same thing

- **Training quantization, chosen by us.** QLoRA freezes the base in 4-bit NF4
  (bitsandbytes) and trains bf16 adapters on top, with
  `bnb_4bit_compute_dtype=bfloat16` and double quantization. This is how the
  weights fit in 24 GB; it is not a property of the submitted artifact.
- **Serving quantization, fixed by the competition.** The scorer serves
  `gemma-4-e4b-it-qat-w4a16-ct`: quantization-aware training, 4-bit weights, 16-bit
  activations, compressed-tensors format. Nobody chooses it.

An adapter trained over NF4 loads onto the W4A16 base because it is a delta over
the same weight shapes, but the two bases are not bit-identical, so a small
quality delta is expected. S5 measures it: load the adapter through
`adk_submission.VllmServer` exactly as the scorer does, before any task runs.

If that delta turns out to matter, the fallback is to train the adapter over the
**dequantized** competition checkpoint, so the training base and the serving base
are the same weights. It is more work to set up; it should be chosen only when the
measurement asks for it.

Practical starting point, to be measured in S4 rather than assumed: 4-bit NF4 base,
LoRA rank 16 on the attention and MLP projections, sequence length 8192,
micro-batch 1 with gradient accumulation, gradient checkpointing on. The 3090 is
Ampere and supports bf16 compute.

Three consequences worth stating early:

1. The adapter is trained against the **unquantized** `gemma-4-e4b-it` and
   applied to the quantized `gemma-4-e4b-it-qat-w4a16-ct` the scorer serves; the
   competition host confirmed the unquantized variants are published for exactly
   this purpose. The quality delta that crossing quantizations introduces is a
   measurement (S5), not a footnote.
2. Training happens **off Kaggle**, on the 3090. Nothing about the workflow
   touches the L4 quota.
3. **The 3090 runs one model at a time, and that model is the student.** Trajectory
   generation goes to the API, so it can run while the card trains, and neither
   workload waits for the other.

## Data

Available today: 129 tasks in `data/raw/tasks.jsonl`, each with `problem_statement`,
`hints_text`, `patch` (the gold fix) and `test_patch`. Plus every artifact the
harness already writes: `traces/` (ATIF v1.7 JSON with each tool call and its
observation), `patches/` and `test_outputs/`.

### The leakage problem, and the split

Training on the same 129 tasks we evaluate on would make every later number
meaningless. The split is fixed now, before any data exists:

- **train**: 100 tasks.
- **holdout**: 29 tasks, never seen by training, never used for checkpoint
  selection.
- Stratified by repository so the holdout keeps the corpus shape (fastapi ~15,
  rich ~11, requests ~3, httpx 0-1).

`dev-v1` stays as a second contrast set for A/B runs, unchanged.

### Where the trajectories come from

**The teacher is `deepseek-v4.1-flash` through the `api` backend, not a local
model.** The reason is the card: the 3090 is for training. Serving a teacher next
to it would either not fit or would force the two workloads to take turns. The
API path already exists and is exercised by the host trial — `DEFAULT_BACKEND =
"opencode"`, `DEFAULT_HARNESS_MODEL = "deepseek-v4.1-flash"`,
`https://opencode.ai/zen/go/v1` behind the `x-opencode-session` forwarding proxy
in `scripts/host-trial/run_host_trial.py` — and the notebook already carries
`MODEL_BACKEND = "api"` with the same preset.

Rejection sampling, unchanged in shape:

1. Run the teacher over the 100 train tasks through the same harness and the same
   system prompt and tool schemas the agent uses at inference.
2. Keep a task only if it ends `resolved` **and** its patch scope is `src_only`
   (no scratch, no docs, no test edits).
3. Cap the kept trajectory at the shortest successful one per task: a longer
   trajectory teaches a style the student cannot afford.

Before the 100-task batch, a **5-task pilot** measures three things the plan
otherwise guesses: accepted trajectories per task, tokens per accepted
trajectory, and therefore the cost of the batch. The pilot's numbers, not an
estimate, decide whether the batch runs as is, with a cheaper teacher, or with
the 31B fallback.

The 31B remains the fallback teacher, served on Kaggle rather than on the 3090 —
it never needed this card. It is the fallback and not the default because its
measured rate on this corpus is 0.246, which caps the dataset at roughly 25
accepted trajectories out of 100.

The competition permits external models that are reasonably accessible, and
training data is not a submitted artifact.

### What to train on

Not the final patch alone. The model is scored as a tool-calling agent: system
prompt, tool schemas, multi-turn loop. Training on `problem -> diff` puts the
adapter off-distribution.

Train on the **decision points**: the assistant turns of an accepted trajectory,
with the exact system prompt, tool definitions and observation formatting the
harness uses at inference. The loss applies to the assistant turns only.

## Pipeline

| Stage | Artifact | Done when |
|-------|----------|-----------|
| S0 | `experiments/subsets/ft-train.json`, `ft-holdout.json` | the split is committed and deterministic |
| S1 | `trajectories/` (git-ignored) | the 31B has run the 100 train tasks through the harness |
| S2 | `dataset/train.jsonl` | accepted trajectories converted to chat format, leakage-checked against the holdout |
| S3 | `dataset/stats.json` | token length distribution, turn counts, acceptance rate |
| S4 | `train/qlora_3090.yaml` | one measured step and one measured epoch time on the 3090 |
| S5 | `adapters/e4b-sft-*/` | adapter trains, loads, and serves through vLLM with the harness |
| S6 | run under `runs/` | holdout and `dev-v1` measured against the baseline |
| S7 | `submission/adapters/<name>/` | `pack submission --check` green with the adapter inside |

S5 has a gate that is easy to skip and expensive to miss: an adapter that trains
but does not load into the served quantized model is worthless. Load it through
`adk_submission.VllmServer` exactly as the scorer does before spending a run.

## Evaluation protocol

Pre-declared, per `docs/dev-experiment-loop.md`: the component under test is the
adapter, everything else fixed. The comparison is the E4B baseline measured today
on the same tasks. Report, in this order:

1. Holdout resolution (29 tasks) as the only selection signal.
2. `dev-v1` (11 tasks) as the secondary contrast.
3. The 129-task corpus only after S6 passes, and never as a selection signal.
4. Tool calls and wall time per task, because the 12 h run budget still binds.

An adapter that improves holdout but doubles the mean wall time is a regression:
the scored run has no room left.

## Packaging for the competition

- `submission/adapters/<name>/adapter_config.json` plus
  `adapter_model.safetensors`; PEFT format, rank <= 128.
- One base model per submission; the adapter does not change that. The manifests
  already declare `gemma-4-e4b-it-qat-w4a16-ct` and must keep declaring it.
- Total unpacked archive under 3 GiB including adapters; a rank-16 adapter on
  this model is well inside it.
- No network, pip, MCP or subprocess strings under `submission/`; training code
  never ships.
- `pack submission --check` runs on every PR that touches the adapter.

## Risks

| Risk | Why it matters | Mitigation |
|------|----------------|------------|
| Overfitting to 100 public tasks | the hidden set is drawn from private repositories | holdout, early stop on holdout loss, keep the adapter small |
| Tool-call format drift | the scorer rejects malformed calls and the task dies | keep the system prompt and tool schemas identical to inference |
| Catastrophic forgetting | the base model's general skill is all we have | rank 16, few epochs, learning rate low, evaluate on `dev-v1` |
| 3090 throughput | a 100-trajectory epoch at 8k tokens is not instant | gradient checkpointing, micro-batch 1, measure before scaling |
| Adapter does not load in the served model | silent zero | S5 loads it through the same server path the scorer uses |
| Teacher yield too low | fewer than 15 accepted trajectories | the 5-task pilot catches it before the batch; fall back to the 31B on Kaggle |
| Capacity gap between teacher and student | a much stronger teacher produces trajectories the 4B model cannot imitate, and the adapter learns an unreachable style | keep the shortest successful trajectory per task, keep rank small, judge only on holdout |
| Tool-call shape drift from the API teacher | the harness normalises the teacher's calls through LiteLLM, so the transcript format may not match what the student must emit natively | keep only turns whose calls the harness actually executed; compare the emitted format against a base-model sample before training |
| API cost | 100 multi-turn agent runs with a 32k window are not free | the 5-task pilot measures tokens per accepted trajectory before the batch |

## Kill criteria

Stop and say so, rather than iterate blindly:

- after S4, if one epoch on 100 trajectories exceeds **12 hours** on the 3090,
  the plan does not fit the calendar and needs a smaller sequence length or a
  smaller training set;
- after S6, if holdout does not beat the baseline by at least **3 tasks**, the
  method has not shown signal on this corpus;
- after two adapter iterations without holdout movement, stop tuning and keep the
  base model.

## Open questions

1. Does `deepseek-v4.1-flash` resolve enough of the 100 train tasks to be worth
   its cost? The 5-task pilot answers it; the plan does not assume a rate.
2. Which target modules give the best adapter per VRAM byte on this
   architecture? S4 answers it empirically, not by convention.
3. Is the hidden set's repository mix the same as the public one? If it is not,
   a corpus-proportional holdout understates the risk.
